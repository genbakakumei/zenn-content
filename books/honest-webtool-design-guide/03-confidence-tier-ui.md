## この章の狙い

前章で扱った「送らない設計」がプライバシーの誠実さだとすれば、この章で扱うのは**精度の誠実さ**です。計算ツールは「入力すれば数値が出る」という体験そのものが説得力を持つため、確からしさの違う数値を同じ見た目で出しても、機能としては何の問題もなく動いてしまいます。問題が表面化するのは、ユーザーがその数値を鵜呑みにして判断を誤った後です。

この章では、確信度が異なる数値を区別して表示するための3状態パターン(confirmed / estimate / unavailable)を、単一の値だけでなく**複数の値を組み合わせて1つの結果を出す場面**まで広げて扱います。

## 3状態パターンの復習と、実装の骨格

まず基本形を確認します。判定ロジック(JS側)と見た目(CSS側)を分離し、状態は `data-confidence` 属性1つに集約します。

```js
function renderResult(el, { confidence, value, note }) {
  el.dataset.confidence = confidence; // confirmed / estimate / unavailable
  el.querySelector('.result__value').textContent = value ?? '';
  el.querySelector('.result__note').textContent = note ?? '';
}
```

この形自体は前章までの延長ですが、実務で悩みやすいのは「1つの結果が複数の計算の合成でできている」場合です。次節で具体的に扱います。

## 合成結果の確信度: 最弱の状態を継承する

工数計算ツールのように、複数の入力項目(作業ごとの数量×歩掛)を合計して1つの結果(総人工数)を出すツールでは、項目ごとに確信度が異なることがあります。たとえば「歩掛の数値をユーザー自身が入力した項目」は confirmed(入力通りに一意に計算できる)ですが、「歩掛が未入力でツール側の暫定値を仮に当てはめた項目」があれば、その項目は estimate になります。

このとき、**合計結果の確信度は、内訳の中で最も確信度が低いものを継承する**という原則を置くと、判断がぶれません。

```js
const CONFIDENCE_RANK = { confirmed: 0, estimate: 1, unavailable: 2 };

function aggregateConfidence(items) {
  // 内訳の中で最も確信度が低い(ランクが大きい)ものを全体の確信度とする
  return items.reduce((worst, item) =>
    CONFIDENCE_RANK[item.confidence] > CONFIDENCE_RANK[worst]
      ? item.confidence
      : worst
  , 'confirmed');
}
```

「一部が参考値なら全体も参考値」という単純なルールですが、これを決めておかないと、実装者ごとに「多数決」「平均」「無視して confirmed 扱い」といったブレが生まれます。特に「無視して confirmed 扱い」は、精度を盛る事故そのものなので、明示的に禁止しておく価値があります。

## unavailable を選ぶ基準: 「出せるが、出すべきでない」場合

3状態のうち、estimate と unavailable の境界は実装者の判断が割れやすいところです。目安として、次の問いに「はい」と答えられるかどうかで仕分けます。

| 問い | はい → | いいえ → |
|---|---|---|
| 前提条件(チェックボックス等)を明示すれば、その前提の範囲内で意味のある数値になるか | estimate として表示し、前提と注記を添える | unavailable を検討 |
| 数値を見たユーザーが、注記だけで「参考値である理由」を理解できるか | estimate | unavailable |
| 数値を出すこと自体が「専門家に相談すべき論点を、相談不要であるかのように見せてしまう」か | unavailable | estimate |

3つ目の問いが重要です。有給休暇計算ツールにおける「休職期間中の個別出勤率」のように、そもそも入力項目の粒度では確定しようがない論点は、estimate(参考値)としてでも数値化してしまうと、「専門家に確認すべき事項である」という前提自体が見えなくなります。この場合は数値を出さず、unavailable として理由と代替手段(専門家への確認)だけを示すほうが誠実です。

## テストケースとしての3状態

3状態パターンは表示の話であると同時に、そのままテスト観点にもなります。6章「エージェントによる自己検証」で扱う自己検証の手順に先立ち、実装完了時点で最低限確認すべきケースを挙げておきます。

- confirmed になるべき入力で、estimate や unavailable のバッジが誤って出ていないか
- estimate に切り替わる条件(チェックボックスのON/OFF、非対応モデルの選択など)が、実際にその条件でのみ発火するか
- unavailable のとき、数値表示領域が空白のまま放置されず、理由と代替手段の注記が必ず表示されるか
- 合成結果を扱うツールでは、内訳の一部だけを estimate/unavailable に変えたときに、全体の確信度が正しく最弱側へ引きずられるか

## まとめ

- 確信度は個々の値だけでなく、複数の値を合成した結果にも一貫させる必要があり、「最弱の状態を継承する」ルールを明文化しておくとブレを防げる
- estimate と unavailable の境界は、「前提条件を明示すれば意味を持つか」「専門家に相談すべき論点を隠してしまわないか」という問いで仕分けられる
- 3状態パターンはUI設計であると同時に、実装後に確認すべきテスト観点の一覧としても機能する

次章では、精度の誠実さの延長として、労務・法律のように「制度は明確だが個別事情に依存する」領域で、どこまでを機械的に計算してよいかの線引きを扱います。
