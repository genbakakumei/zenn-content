## この章の使い方

ここまでの6章では、送らない設計(第2章)・精度を偽装しないUI(第3章)・規制領域の線引き(第4章)・ブラウザ内完結の実装Tips(第5章)・エージェントによる自己検証(第6章)・費用ゼロの技術選定(第7章)を、それぞれ独立したテーマとして深掘りしてきました。本章はその総まとめとして、**新しい計算・変換ツールを公開する前に、まとめて何を確認すべきか**を1つのチェックリストに再構成します。

各項目の詳しい設計パターンは対応する章に譲り、ここでは「点検表」として使えることを優先してまとめています。新しいツールを公開する直前、あるいは既存ツールに機能を追加したタイミングで、このページだけを見返して点検できるようにするのがねらいです。

## チェックリスト

### 1. 「送らない」主張が、4つの崩壊経路すべてで成立しているか(→第2章)

`fetch`・`XMLHttpRequest`等の不使用だけでは不十分です。外部CDNからのスクリプト読み込み、アクセス解析タグが入力ページに同居していないか、`localStorage`等への不要な永続化がないかまで、機能追加のたびに確認する必要があります。ユーザー自身が開発者ツールのNetworkタブで再現できる確認手順を用意できているかも、あわせて点検します。

### 2. 合成結果の確信度が「最弱の状態を継承」しているか(→第3章)

複数の値を組み合わせて1つの結果を出すツールでは、内訳の一部が estimate や unavailable になった瞬間、全体の確信度もそこへ引きずられる実装になっているかを確認します。「一部を無視して confirmed のまま表示する」実装になっていないかは、特に重点的に見るべき箇所です。

### 3. 「計算していい範囲」を3段階で仕分け、スコープ外には注記があるか(→第4章)

機能を作り込む前に、「入力から一意に決まるか」「前提条件を明示すれば意味を持つか」「専門家への相談が必要か」の3段階で仕分けられているかを確認します。3段階目(相談を促すのみ)に分類した論点を、機能として実装しようとしていないか、免責文言が責任範囲の宣言になっているかも点検対象です。

### 4. 日付・数表・描画の境界値が、既知の落とし穴を踏んでいないか(→第5章)

月単位の日付加算が月末日・うるう年で壊れていないか、段階的に増える数表がしきい値比較ではなく整数インデックスで実装されているか、日本語テキストの折り返しが文字単位+実測で行われ「1文字も入らない行」のガードがあるかを確認します。

### 5. 期待値の出どころが、実装コードと独立しているか(→第6章)

ゴールデンパスのテストで使っている期待値が、「実装者が思い出しながら書いた数字」になっていないかを確認します。法令・公開された数表、手計算、既知の境界値という3種類の基準値のうち、最低でも2種類は使って突き合わせているかが目安です。

### 6. 外部依存がビルド時に閉じ込められ、実行時に残っていないか(→第7章)

npmパッケージを使う場合でも、実行時にブラウザがfetchするのは自分のドメインのファイルだけになっているかを確認します。共通コンポーネント(配色・カード・警告バッジ等)がツールごとにコピペで増えていないか、共有ディレクトリから参照する構成になっているかも点検対象です。

## 点検表(印刷・コピペ用)

6項目すべてを毎回フルチェックする必要はありません。新しいツールを公開する直前、あるいは既存ツールに計算ロジックや表示に関わる機能を追加したタイミングで、次の表に沿って見直す使い方を想定しています。

```markdown
## 公開前チェック: <ツール名>

- [ ] 1. 「送らない」主張が4経路すべてで成立している(外部CDN・解析タグ・永続化含む)
- [ ] 2. 合成結果の確信度が「最弱の状態を継承」している
- [ ] 3. 計算していい範囲が3段階で仕分けられ、スコープ外には注記がある
- [ ] 4. 日付・数表・描画の境界値が既知の落とし穴を踏んでいない
- [ ] 5. 期待値の出どころが実装コードと独立している(2種類以上の基準値で突合済み)
- [ ] 6. 外部依存がビルド時に閉じ込められ、実行時に残っていない

判定: 6項目のうち未チェックが1つでもあれば、公開前にその項目を先に埋める
```

**この6項目のどれかが欠けたまま公開するのは避けた方がよい**というのが、実際に5本のツールを運用してきた実感です。特に1番(送らない設計)と3番(規制領域の線引き)は、ユーザーの信頼とツールの法的な立ち位置に直結するため、優先して埋めるべき2項目です。

## 本書のふりかえり

第2章から第7章までの内容を、1つの流れとして振り返ります。

1. **送らない設計**(第2章)が、プライバシーの誠実さを「言うだけ」から「検証できる」ものに格上げする土台になる
2. **精度を偽装しないUI**(第3章)が、送らない設計の裏返しとして生まれる精度の限界を、ユーザーに誠実に見せる
3. **規制領域の線引き**(第4章)は、3状態表示と同じ判断軸の別の顔であり、「何を実装するか」と「どう見せるか」を一致させる
4. **ブラウザ内完結の実装Tips**(第5章)が、1〜4章で決めた設計判断を、境界値のバグで裏切らないための具体的な書き方を提供する
5. **エージェントによる自己検証**(第6章)が、5章までの実装が本当に正しいかを、実装から独立した基準値で確かめる
6. **費用ゼロの技術選定**(第7章)が、ここまでの設計をツール1本だけでなく、本数が増えても崩れない形で維持する

どれか1つだけを整えても誠実さは完成しません。送らない設計があっても精度表示が盛られていれば主張は半分になりますし、規制領域の線引きができていても境界値のバグが残っていれば、仕分けそのものが意味を失います。6つの章は独立したテーマである一方、**同じ「誠実さ」という軸を別の角度から支え合う設計**になっています。

## おわりに

本書で扱ったパターンは、特定の計算ロジックやドメインの知識ではなく、**どの個人開発ツールにも応用できる判断の手順**です。筆者自身、これらの判断基準を先に完成させてからツールを作ったわけではなく、実在する5本のツールを順番に作る中で、「ここを曖昧にしたまま公開していたら、後で信頼を損ねていた」という場面を積み重ねながら言語化してきました。

同種の機能がいくらでも存在する検索市場で、個人開発ツールが選ばれ続ける理由を機能の多さではなく設計の誠実さに置きたいと考えている方にとって、本書のチェックリストが、公開前の最後の点検表として役立てば幸いです。
