## この章の狙い

2〜4章では、「何を実装してよいか」「どう見せるか」という設計判断を扱ってきました。この章は一段実装寄りに降りて、**その設計判断を裏切らないコードをどう書くか**を扱います。せっかく「送らない設計」「精度を偽装しないUI」「規制領域の線引き」を正しく設計しても、実装そのものが境界値でバグっていては、正確性の主張が崩れてしまいます。

実在するツール(有給休暇計算ツール・電子小黒板ジェネレーター)の実装から、ブラウザ内で完結させたまま正確さを担保するための3つの具体的なパターンを取り上げます。

## 1. 日付計算: 月加算を安全に実装する

「入社日から6か月後」のように日付へ月単位で加算する処理は、業務系ツールで頻出します。JavaScriptの`Date.setMonth()`をそのまま使うと、月末日の入力で必ず壊れます。

```js
// 一見動きそうだが、月末日の入力で壊れる実装
function addMonthsNaive(date, months) {
  const d = new Date(date.getTime());
  d.setMonth(d.getMonth() + months);
  return d;
}
```

2023年8月31日に6か月を加算すると、`setMonth`は2024年2月に月だけを進めた上で「31日」を維持しようとします。しかし2024年のうるう年でも2月は29日までしかないため、日付は繰り上がって2024年3月2日になってしまいます。「6か月後」のつもりが2月をまるごと飛び越えてしまうわけです。

対策は、月を加算する間は日を1日に固定して繰り上がりを起こさせず、月が確定したあとで加算先の月の実際の日数にクランプする、という2段階に分けることです。

```js
function addMonthsSafe(date, months) {
  const d = new Date(date.getTime());
  const day = d.getDate();

  d.setDate(1);                      // 繰り上がりを起こさせないよう1日に退避
  d.setMonth(d.getMonth() + months); // 月だけを安全に加算

  // 加算先の月の末日を求め、元の日をその範囲にクランプする
  const daysInTargetMonth = new Date(d.getFullYear(), d.getMonth() + 1, 0).getDate();
  d.setDate(Math.min(day, daysInTargetMonth));

  return d;
}
```

`new Date(year, month + 1, 0)`は日に`0`を渡すと「指定した月の前日」、つまり対象月の末日を返すJavaScriptの仕様で、うるう年判定を自前で書かずに対象月の日数を求められます。この実装を業務ツールに組み込む際は、月末日+平年2月をまたぐ加算・月末日+うるう年2月をまたぐ加算・30日までの月をまたぐ加算・年をまたぐ加算の4パターンを、最低限の境界値として手計算値と突き合わせておくと安心です。

## 2. Canvas描画: 日本語テキストの折り返しと箱サイズの逆算

Canvas 2D APIでユーザー入力のテキストを画像に合成するツール(証明書ジェネレーター、電子小黒板ジェネレーターなど)では、入力文字列の長さが不定なので決め打ちの幅に収まらない、折り返した結果行数が変わるので箱の高さも決め打ちにできない、という2つの問題に必ずぶつかります。

英語圏の実装例はスペース区切りの単語単位で折り返す前提のことが多く、スペースを含まない日本語では`text.split(' ')`が機能しません。必要なのは「単語」ではなく「文字」を単位にした判定で、`CanvasRenderingContext2D.measureText()`で実際のレンダリング幅を測りながら1文字ずつ詰めていきます。

```js
function wrapLines(ctx, text, maxWidth) {
  const out = [];
  // 手入力の改行(Enter)はそのまま尊重し、長い行だけ折り返す
  text.split('\n').forEach((rawLine) => {
    const chars = rawLine.split('');
    let line = '';
    for (const ch of chars) {
      const test = line + ch;
      if (ctx.measureText(test).width > maxWidth && line.length > 0) {
        out.push(line);
        line = ch;
      } else {
        line = test;
      }
    }
    out.push(line);
  });
  return out;
}
```

ここでの要注意点は`line.length > 0`のガードです。これがないと、1文字だけで`maxWidth`を超えるフォントサイズの場合に空文字列を積み続けて無限ループ、または空行だらけになります。`ctx.font`は呼び出し前に設定しておく必要があり、描画時と異なるフォント設定で測ると幅がずれる点にも注意が必要です。

折り返しが確定すれば、箱の高さは行数から機械的に計算できます。

```js
const fontSize = 16;
const lineHeight = Math.round(fontSize * 1.4); // 1.4 は日本語で読みやすい行間の目安
const pad = 12;

const lines = wrapLines(ctx, rawText, maxWidth);
const boxHeight = pad * 2 + lines.length * lineHeight;
```

`textBaseline = 'top'`にしておくと、`y`座標の計算が「上端 + 行番号 × 行の高さ」で済み、ベースライン基準のオフセット計算をしなくてよくなります。

## 3. 法定数表の実装: 配列+インデックスで境界条件バグを避ける

有給休暇の付与日数、所得税の税率のように、勤続年数や所得階層がしきい値を超えるたびに段階的に値が変わる数表は、法律・制度まわりのツールで頻繁に出てきます。これを`if/else if`の階段で素朴に実装すると、しきい値ちょうどの境界で値がズレるバグを作り込みやすくなります。

```js
// やりがちな実装
function grantDays(years) {
  if (years >= 6.5) return 20;
  if (years >= 5.5) return 18;
  // ...
  return 0;
}
```

`years`を日付の差分から計算した小数で渡すと、うるう年・月末日の丸めの影響で「本来6.5年ちょうどのはずが6.499999...年と評価される」ケースが混入しえます。しきい値比較は、入力が浮動小数点の日数差であるほど境界に弱くなります。

実際の有給休暇計算ツールでは、「勤続年数で分岐する値」を比較演算ではなく、「付与が何回目か」という整数インデックスの配列引きに変換しています。

```js
const FULL_TIME_DAYS = [10, 11, 12, 14, 16, 18, 20];
const PRO_RATA_DAYS = {
  4: [7, 8, 9, 10, 12, 13, 15],
  3: [5, 6, 6, 8, 9, 10, 11],
  2: [3, 4, 4, 5, 6, 6, 7],
  1: [1, 2, 2, 2, 3, 3, 3],
};

function daysForIndex(empType, idx) {
  const i = Math.min(idx, FULL_TIME_DAYS.length - 1); // 7回目以降は最終値に固定
  if (empType === 'full') return FULL_TIME_DAYS[i];
  return PRO_RATA_DAYS[empType][i];
}
```

付与日のスケジュールは「初回基準日から12ヶ月ごとに到来する」という整数の繰り返しなので、「i回目の基準日」という整数インデックスは最初から確定しており、日付計算の丸め誤差が入り込む余地がありません。しきい値比較そのものが式から消えるため、境界条件のバグが原理的に発生しなくなります。上限の据え置きも`Math.min(idx, 配列長 - 1)`という1行のclampで表現でき、「無限に続く仕様」を「有限配列+clamp」という扱いやすい形に落とし込めます。

この変換が成立するのは、しきい値の刻み幅が一定で、かつインデックスが整数カウンタとして得られる場合です。刻み幅が不揃いな数表(所得税の累進税率のように階層の幅がバラバラなもの)では、しきい値の配列を昇順に並べて`Array.prototype.findIndex`で該当区間を探す方式のほうが素直です。

## まとめ

- 月単位の日付加算は「1日に退避してから月を加算し、加算先の月の実際の日数にクランプする」2段階で実装すると、月末日の繰り上がりバグを避けられる
- 日本語テキストの折り返しは、単語単位ではなく文字単位+`measureText`による実測で判定し、「1文字も入らない行を作らない」ガードを必ず入れる
- 段階的に増える法定の数表は、しきい値比較ではなく「何回目か」という整数インデックスで数表配列を引く設計に変換すると、境界条件のバグが原理的に発生しなくなる

いずれも共通するのは、**「存在しない値」や「浮動小数点の誤差」が紛れ込む経路を実装の手前で塞いでおく**という発想です。次章では、こうして書いた実装が本当に正しく動いているかを、どう検証してから「完了」と報告するかを扱います。
