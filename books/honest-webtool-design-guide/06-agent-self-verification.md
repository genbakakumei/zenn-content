## この章の狙い

本書の「AIエージェント自律運用実践ガイド」(本シリーズのもう1冊)の6章では、継続タスク全般における「実装した」と「動いた」のギャップを埋める自己検証の型(ゴールデンパス・エッジケース・クロスデバイス確認など)を扱っています。本章はその型を前提としつつ、**計算ツール特有の問題**に絞って掘り下げます。すなわち、「ゴールデンパスで想定通りの値が出た」というとき、その**想定通りの値はそもそも何と照合して決めたのか**という一段手前の問いです。

ユニットテストが通っていても、期待値そのものが実装者の思い込みと同じ間違いを共有していれば、テストは何も検出しません。法律・制度のように外部に唯一の正解が存在する領域だからこそ使える、具体的な照合先を整理します。

## 自分の期待値を自分でテストする、という循環

次のようなテストは、一見ちゃんと検証しているように見えます。

```js
test('6ヶ月勤続で10日付与される', () => {
  expect(grantDays(0.5)).toBe(10);
});
```

しかし`10`という期待値が「実装者が労基法を思い出しながら書いた数字」である場合、実装側の計算ロジックに勘違いがあれば、同じ勘違いのままテストの期待値も書いてしまう可能性が残ります。ユニットテスト自体は「実装とテストの期待値が一致している」ことしか保証しておらず、「その値が実際に正しい」ことまでは保証しません。

## 3種類の基準値(オラクル)を使い分ける

有給休暇計算・工数計算のようなツールを検証する際に使っている、期待値の出どころは大きく3種類です。

| 基準値の種類 | 具体例 | 検出できるバグ |
|---|---|---|
| 1. 法令・公開された数表そのもの | 労働基準法の比例付与日数表、各値をそのまま転記 | 実装者の思い込みによる数表の誤転記・誤実装 |
| 2. 手計算(電卓・紙) | 入社日から8回分の基準日・付与日数を自分で計算し直す | ロジックの実装ミス(日付計算・分岐の誤り) |
| 3. 既知の境界値(うるう年・月末日) | 2023-08-31入社+6ヶ月が2024-02-29になるか | 日付計算ライブラリ・自作ロジックの境界バグ |

重要なのは、どの基準値も**実装コードを一切経由せずに得られる**という点です。法令の数表はそのまま転記するだけで計算不要、手計算は実装と独立した経路で同じ答えにたどり着く確認、境界値は「2024年がうるう年である」という外部事実から逆算した期待値です。実装のコピーになっていない期待値だけが、実装のバグを検出できます。

3つはそれぞれ別の種類のバグを検出する設計になっています。手計算との突き合わせだけでは比例付与表の転記ミスは見つかりませんし、数表の転記確認だけでは日付計算のロジックバグは見つかりません。どれか1つだけでは「テストが通っている」という安心感だけが残り、カバーできていない種類のバグが未検出のまま残ります。

## Playwrightによる実ブラウザ自己検証への落とし込み

これらのWebツールは1ファイル完結のテスト基盤を持たないため、Playwright(実ブラウザ自動操作ツール)で画面に表示された値を、上記3種類の基準値と突き合わせる形で検証しています。前章までの実装Tipsと対応させると、確認すべき項目は次のように整理できます。

1. **ゴールデンパス**: 法令の数表・手計算のいずれかと、UI上の表示値が一致するか
2. **境界値**: 5章で扱った月末日・うるう年をまたぐ入力で、既知の境界値と一致するか
3. **確信度の切り替え**: 3章で扱った前提条件(出勤率など)が外れたとき、estimate表示に正しく切り替わるか
4. **クロスデバイス・コンソールエラー**: デスクトップ/モバイル幅・ダークモードのスクリーンショットを撮り、コンソールにエラーが出ていないことを確認する

実際に有給休暇計算ツールの検証では、2020-04-01入社・通常の労働者という設定で8回分の基準日・付与日数(10→11→12→14→16→18→20→20日)を手計算し、実装の出力と突き合わせました。比例付与(週2日・週3日勤務)の日数表は労働基準法の別表の数値をそのまま転記して突き合わせ、月末入社(2023-08-31)から6ヶ月後がうるう年の2月末(2024-02-29)に正しく丸まるかという境界値も別途確認しています。

テストフレームワークの有無にかかわらず、「どの基準値と突き合わせているか」さえ明確なら、簡易な確認でも検出力は確保できます。逆にテストコードとして整備されていても、期待値の出どころが実装者の記憶だけなら、先述の循環から逃れられません。

## まとめ

- 計算ツールのテストは、期待値の出どころが実装コードと独立していなければ、実装のバグを検出できない
- 法令・公開された数表、手計算、既知の境界値という3種類の基準値は、それぞれ別の種類のバグを検出するため、1種類だけに頼らない
- Playwrightなどの実ブラウザ検証は、ゴールデンパス・境界値・確信度の切り替え・クロスデバイスという4つの観点に、計算ツール特有の「基準値との突き合わせ」を組み込むことで、はじめて「完了」と報告できる水準になる

次章では視点を変え、こうして作ったツールを複数本並べても費用ゼロを維持するための技術選定を扱います。
