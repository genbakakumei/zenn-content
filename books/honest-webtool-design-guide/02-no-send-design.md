## この章の狙い

「このツールは入力データをサーバーに送りません」という一文は、静的Webツールの説明文でよく見かけます。しかし、この一文をそのまま信じてよいかどうかは、本来ユーザー側では判断できません。実装を見ない限り、「送っていない」と「送っていないと言っているだけ」を区別する手段がないからです。

この章では、「送らない」という主張を**言うだけの誠実さ**から**検証できる誠実さ**に格上げするための、実装レベルの判断基準と手順を扱います。写真や個人情報が写り込みやすい題材(工事写真の電子小黒板ジェネレーター)を例に、他のツールにも展開できる形で整理します。

## 主張が嘘になる4つの経路

「送らない」という主張が、作り手の悪意なしに崩れる経路は限られています。パターンを知っておくと、レビュー時に確認すべき箇所が絞れます。

| # | 経路 | 気づきにくい理由 |
|---|------|-----------------|
| 1 | 処理結果を検証・改善目的で外部APIに送る | 「精度向上のため」という善意の実装として紛れ込む |
| 2 | アクセス解析タグがフォーム値をイベントパラメータに含める | 解析ツールの初期設定のまま入れてしまい、パラメータの中身を確認していない |
| 3 | 外部CDNからスクリプト・フォントを読み込む | 「実行はブラウザ内で完結している」と誤解し、読み込み自体をノーカウントにしてしまう |
| 4 | `localStorage` 等に永続化し、共有端末で情報が残る | 「送信していない」の範囲だけを見て、保存によるリスクを別問題として見落とす |

4つとも「送らないと言った瞬間の実装」は正しくても、機能追加や解析導入といった**後からの変更**で壊れやすいという共通点があります。したがって一度の実装確認では終わらず、機能を追加するたびに同じ確認を繰り返す運用が必要になります(この繰り返し確認の位置づけは7章「費用ゼロの技術選定」でも扱います)。

## 実装チェックリスト

新しいツールに着手するとき、あるいは既存ツールに機能を追加するときに、次のリストを実装のたびに通します。

- [ ] コード全体を検索して `fetch(` / `XMLHttpRequest` / `sendBeacon(` / `WebSocket(` が存在しないことを確認する(存在する場合は、送信先が自分の管理下にあるドメインかどうかを個別に精査する)
- [ ] `<script src="https://...">` のような外部オリジンからのスクリプト読み込みがないことを確認する。ライブラリが必要な場合は `vendor/` にビルド済みファイルとして同梱し、同一オリジンから配信する
- [ ] アクセス解析タグ(GA4等)を導入する場合、ツール本体の入力ページには置かず、トップページやランディングページなど個人データに触れないページに限定する
- [ ] 画像・ファイルは `Image` オブジェクトや `Canvas` 上でのみ扱い、`localStorage` / `IndexedDB` に保存しない設計にする(ダウンロード操作でユーザー自身の端末に保存されるのは対象外)
- [ ] 開発者ツールのNetworkタブでの確認手順を、README または UI 上の注記として明文化する

最後の項目が、次節で扱う「ユーザー自身による検証」につながります。

## 電子小黒板ジェネレーターの実装から

実際に公開準備を進めている電子小黒板ジェネレーター(工事写真に黒板を合成するツール)は、上記チェックリストをそのまま満たす実装になっています。

```js
// 写真の読み込みから合成までブラウザ組み込みAPIのみで完結する
function loadPhoto(file) {
  const reader = new FileReader();
  reader.onload = (e) => {
    const img = new Image();
    img.onload = () => drawComposite(img); // Canvas 2D へそのまま渡す
    img.src = e.target.result;             // data URL。ここでも外部送信は発生しない
  };
  reader.readAsDataURL(file);
}
```

このコードには `fetch` も `XMLHttpRequest` も登場しません。写真データはブラウザのメモリ上(`FileReader` の読み取り結果と `Canvas` のピクセルデータ)だけを行き来し、ダウンロード操作(`<a download>` によるBlob URLの生成)以外でファイルシステムやネットワークに触れる箇所がありません。工事写真という、現場の所在地・作業内容が写り込みうる機微なデータを扱うツールだからこそ、この実装の単純さそのものが訴求点になります。

## ユーザーに検証させる: Networkタブ確認手順のテンプレート

実装が正しくても、ユーザーがそれを信じる理由がなければ主張は弱いままです。技術者でなくても再現できる確認手順を、README やツールのフッターに用意しておきます。

```markdown
### このツールがデータを送っていないことを確認する方法

1. このページを開いた状態で、ブラウザの開発者ツール(F12キーなど)を開き、
   「Network」または「ネットワーク」タブを選択する
2. 通常通り操作する(写真を選ぶ、入力する、ダウンロードするなど)
3. 最初にページを読み込んだとき以外、リクエストが増えていないことを確認する
   (増えている場合は、宛先のドメインを確認してください)
```

この手順を用意すること自体が、「送らない設計」を機能としてではなく**信頼設計**として扱っていることの証明になります。手順を書けるということは、実装者自身がその主張に自信を持っているという裏付けでもあります。

## まとめ

- 「送らない」という主張は、`fetch` 等の不使用に加えて、外部CDN・解析タグ・永続化ストレージという周辺要素まで揃って初めて成立する
- 主張が崩れる経路は概ね4パターンに絞り込め、いずれも機能追加のタイミングで再発しやすいため、実装のたびにチェックリストを通す運用にする
- ユーザー自身が開発者ツールで再現できる確認手順を明文化すると、主張が「言うだけ」から「検証可能」に変わる

次章では、送らない設計と対になる論点として、「送らないからこそ生まれる、精度の限界」をどうUIで誠実に見せるかを扱います。
