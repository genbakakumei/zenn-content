## なぜファイルに書き出すだけで十分なのか

エージェントの「記憶が消える」問題への対処法として、ベクトルDBによる長期記憶や、専用の状態管理サービスを検討したくなるかもしれません。しかし個人開発・スモールビジネスの規模では、**Gitリポジトリ内の3種類のMarkdownファイル**で十分に機能します。理由は単純で、Gitリポジトリ自体が「差分の履歴付き・改ざん検知可能・人間にも読める」状態ストアだからです。専用DBを持ち込むと、それ自体が固定費・運用対象になり、費用ゼロ運用の原則に反します。

3ファイルとは以下の役割分担です。

1. **ブートストラップファイル**(本書では `OPERATIONS.md`)— 起動直後に必ず読む「運用マニュアル」
2. **ステートレジャー**(本書では `ACCOUNTS.md`)— 外部状態(アカウント・依頼中タスク)の台帳
3. **作業ログ**(本書では `WORKLOG.md`)— 時系列の実行履歴と、次回への申し送り

## 1. ブートストラップファイル

役割は「エージェントが迷わず正しい手順で再開できること」だけです。書くべきものと書かないものを分けるのがコツです。

**書くべきもの**
- リポジトリ構成の地図(どこに何があるか)
- 恒久的なルール・制約(費用ゼロ、公開判断基準など)
- 定期実行の一覧とその役割
- 「セッション開始時に必ずやること」の手順

**書かないもの**
- 個別の進捗状況(→ ステートレジャーや作業ログに書く)
- 一度きりの判断の経緯(→ 作業ログに書く。ブートストラップに書くと肥大化し続ける)

ブートストラップファイルが肥大化する最大の原因は、「今回だけの事情」を書き足してしまうことです。恒久ルールと一時的な申し送りを混ぜないことが、長期運用での可読性を保つ鍵になります。

```markdown
# OPERATIONS.md — セッション再開時に必ず最初に読むこと

## 全体像
- 状態台帳: ACCOUNTS.md
- 作業ログ: WORKLOG.md
- 事業計画: BUSINESS_PLAN.md

## 恒久ルール
1. 費用が発生する契約は一切禁止
2. 個人情報は公開物に含めない
3. 品質基準を満たさないものは公開しない

## 定期実行の状態
- 月曜: 週次レポート
- 火曜: コンテンツ制作バッチ
- 水曜: プロダクトセッション
```

## 2. ステートレジャー

「今、外部世界がどういう状態か」を管理する台帳です。特に重要なのが、**人間にしかできないタスクの状態管理**です。ステータスは3値で十分機能します。

```
未依頼 → 依頼中 → 完了
```

各エントリには「何を」「どこで」「完了したら何が起きるか」を書きます。ここで重要なのは、**完了判定の主語を人間からエージェントに移す**ことです。「オーナーに完了報告してもらう」のではなく、「次回起動時にエージェント自身がリポジトリやAPIの状態を見て完了を検知する」設計にすると、人間側の負担が「一言connect」だけになります。

```markdown
## 3. Booth
- ステータス: 依頼中
- 手順: pixivアカウント作成 → Boothでショップ開設
- 完了検知: このファイルの本エントリを更新してもらうか、
  次回セッションでショップURLの有無を確認する
```

ステートレジャーは「今アクティブな状態」だけを持つのが原則です。完了して以後変化しない情報(認証情報の所在、恒久的な運用ルール)はブートストラップ側に、時系列の経緯は作業ログ側に移し、レジャー自体は常に短く保ちます。

## 3. 作業ログ

新しい日付を上に追記する、Gitでいうcommit logに近いものです。各エントリに固定フォーマットを持たせることで、後から`grep`や人間の目視で拾いやすくなります。

```markdown
## YYYY-MM-DD(曜日・セッション種別)

### やったこと
(実施内容を箇条書き)

### 次のセッションへの申し送り
1. (次回最優先で確認・実行すべきこと)
2. ...

### 数字
(売上・費用・公開数など、事業のKPIを一行で)
```

**「次のセッションへの申し送り」が最も重要な項目です。** ここが空だったり抽象的だったりすると、次回起動時のエージェントは「前回何を意図していたか」を復元できず、同じ探索をやり直すか、間違った優先順位で動きます。申し送りは「何をすべきか」だけでなく「なぜ後回しにしたか」「何を待っているか」まで書くと、次回セッションが同じ探索を繰り返さずに済みます。

## 3ファイルの読み書き順序

起動時は必ず **ブートストラップ → ステートレジャー → 作業ログ** の順で読みます。この順序には理由があります。

- ブートストラップを先に読むことで、その後の情報をどの文脈で解釈すべきかが決まる
- ステートレジャーを読むことで、「今すぐ着手できる外部要因の変化」があるかを把握する
- 作業ログを最後に読むことで、直近の意思決定の続きから再開できる

終了時は逆に、**作業ログへの追記を最後のアクション**にします。これにより、途中でエラーが起きてセッションが中断しても、少なくとも「ログを書く前に落ちた」ことが次回起動時にすぐ分かります(=前回のログの申し送りが存在しない、または「未完了」の記載がある状態から異常検知できる)。

## この章のまとめ

- 専用の記憶DBを持ち込まず、Gitリポジトリ内の3ファイルで状態を外部化する
- ブートストラップ(恒久ルール)・レジャー(現在の外部状態)・ログ(時系列履歴)は役割を厳密に分離する
- 完了判定の主語を人間からエージェントへ移し、人間の負担を最小化する
- 起動時と終了時の読み書き順序を固定し、中断からの異常検知も設計に組み込む

次章では、この3ファイルパターンを前提に、「どこまでエージェントに権限を渡すか」という境界線の設計を扱います。
