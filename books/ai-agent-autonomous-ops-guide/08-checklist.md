## この章の使い方

ここまでの7章では、状態管理(第2章)・権限委譲の境界線(第3章)・人間依存タスクの扱い(第4章)・スケジュール実行(第5章)・自己検証(第6章)・費用ゼロの技術選定(第7章)を、それぞれ独立したテーマとして深掘りしてきました。本章はその総まとめとして、**新しく継続タスクをエージェントに任せる前に、まとめて何を確認すべきか**を1つのチェックリストに再構成します。

各項目の詳しい設計パターンは対応する章に譲り、ここでは「点検表」として使えることを優先した形にまとめています。新しい継続タスクを立ち上げるとき、あるいは既存タスクの権限やスコープを広げるときに、このページだけを見返して点検できるようにするのがねらいです。

## チェックリスト

### 1. 不可逆な操作の許可リストが明文化されているか(→第3章)

削除・公開・送金・契約など、後戻りできない操作を、エージェントが独自の裁量で実行してよいか、それとも人間の承認が必要かを事前に線引きしておく必要があります。「常識的に判断してくれるはず」という期待に頼ると、エージェントの解釈と人間の期待がズレたときに取り返しがつきません。

### 2. 状態が人間の記憶やチャット履歴ではなく、外部ファイルに外部化されているか(→第2章)

エージェントのセッションは途中で切れたり、会話履歴が要約されたりします。「今どこまで進んでいて、次に何をすべきか」がチャットの記憶だけに依存していると、セッションが変わった瞬間に文脈が失われます。運用マニュアル・状態台帳・作業ログをファイルとして外部化し、次のセッションが必ずそこから再開する仕組みを作っておくべきです。

### 3. 人間依存タスクが「選ぶだけ」の粒度までバッチ化され、催促しないルールがあるか(→第4章)

アカウント登録や契約など、人間にしかできない作業は必ず出てきます。これを都度エージェントが催促すると、人間側の負担が積み重なって信頼を消耗します。依頼は定期的にまとめてバッチ化し、かつ「未対応でも催促しない」ルールを決めておくことで、待機コストに振り回されずに他の作業へ進めます。

### 4. 実行トリガーの権限スコープが狭く、暴走時に止める手段があるか(→第5章)

継続タスクをスケジュール実行に乗せる際は、そのトリガーがどこまでの権限を持つか、そして異常な挙動をしたときに人間側から止められるかを確認しておく必要があります。実行回数や間隔を絞り、必要なリポジトリ・サービスだけにアクセスを限定しておくことで、想定外の暴走の被害範囲を小さくできます。

### 5. 成果物の動作確認(自己検証)まで自動化に含まれているか(→第6章)

「実装した」と「動くことを確認した」は別物です。特に人間が毎回目視確認しない前提の継続タスクでは、エージェント自身がゴールデンパスとエッジケースを検証してから完了報告する仕組みが必要です。検証を省略すると、壊れた成果物が誰にも気づかれないまま積み上がるリスクがあります。

### 6. 費用が発生しない技術選定になっているか(→第7章)

継続タスクは1回の判断ミスより、気づかないまま積み重なる従量課金の方が実害が大きくなりがちです。無料枠を超えると自動課金が発生するサービスを使っていないか、ハードキャップ(請求上限)を設定できているかを事前に確認しておく必要があります。

### 7. 異常時に人間へ通知する経路が用意されているか(→第3章・第5章)

継続タスクは「順調に回っている間は人間が見なくていい」ことが利点ですが、裏を返せば異常が起きても誰も気づかないリスクと表裏一体です。定期的なサマリー通知に加えて、明らかな異常(エラーの連続発生、想定外の費用発生の兆候など)を検知したときに、通常のレポート頻度を待たずに人間へ知らせる経路を用意しておくべきです。

## 点検表(印刷・コピペ用)

7項目すべてを毎回フルチェックする必要はありません。継続タスクを新しく任せる最初の1回、あるいは権限やスコープを広げるタイミングで、次の表に沿って設計を見直す使い方を想定しています。

```markdown
## 継続タスク着手前チェック: <タスク名>

- [ ] 1. 不可逆操作の許可リストが明文化されている
- [ ] 2. 状態が外部ファイルに外部化されている
- [ ] 3. 人間依存タスクが「選ぶだけ」の粒度でバッチ化されている
- [ ] 4. 実行トリガーの権限スコープが狭く、止める手段がある
- [ ] 5. 自己検証(動作確認)が完了報告の前提になっている
- [ ] 6. 費用ゼロ(またはハードキャップ付き)の技術選定になっている
- [ ] 7. 異常時に人間へ通知する経路がある

判定: 7項目のうち未チェックが1つでもあれば、着手前にその項目を先に埋める
```

**この7項目のどれかが欠けたまま継続タスクの範囲を広げるのは避けた方がよい**というのが、実際に運用してきた実感です。特に2番(状態の外部化)と1番(不可逆操作の許可リスト)は、他の項目の前提になっているため、優先して埋めるべき2項目です。

## 本書のふりかえり

第2章から第7章までの内容を、1つの流れとして振り返ります。

1. **状態を外部化する**(第2章)ことで、記憶が消えるエージェントでも継続稼働できる基盤ができる
2. **権限の境界線を決める**(第3章)ことで、その基盤の上でどこまで自律的に動いてよいかが明確になる
3. **人間依存タスクが止まったときの振る舞い**(第4章)を決めることで、境界線4(バッチ化)の運用が長期化にも耐えられる
4. **スケジュール実行**(第5章)が、これらのルールを実行環境に固定し、継続的に回し続ける仕組みになる
5. **自己検証**(第6章)が、スケジュール実行によって生み出される成果物の品質を、人間の目視確認なしに担保する
6. **費用ゼロの技術選定**(第7章)が、これら全体を財務的なリスクなしに継続させる土台になる

どれか1つだけを導入しても運用は安定しません。状態の外部化がなければ境界線は毎回口頭で説明し直すことになり、自己検証がなければスケジュール実行は不具合を量産する仕組みになりかねません。7つの章は独立したテーマである一方、**互いの前提を支え合う設計**になっています。

## おわりに

本書で扱ったパターンは、いずれも特定のプラットフォームやAIモデルに依存しない、汎用的な設計判断です。筆者自身、これらのパターンを完成させてから事業を始めたわけではなく、実際に運用する中で「これを決めていなかったせいで詰まった」という経験を積み重ねながら言語化してきました。

継続的にAIエージェントへタスクを任せようとしている方にとって、本書のチェックリストが、同じ詰まり方を繰り返さないための最初の点検表になれば幸いです。
