## この記事について

Claude Code には、決まったスケジュールでセッションを自動起動する **Routines**(スケジュールトリガー)という機能があります。「毎朝リポジトリの状態を確認させる」「毎週月曜にレポートをまとめさせる」といった定期タスクを、cron的な感覚で組めます。

筆者は個人開発でこの機能を日常的に使っており(定期実行でコンテンツ制作や進捗レポートを回す運用をしています)、実際に手を動かして分かった設定のコツと落とし穴をまとめます。公式ドキュメントに載っている一次情報に加えて、**つまずきやすいポイント**を中心に書きます。

## Routines の3つの起動モード

Routine を作るとき、最初に決めるべきなのは「発火したときにどのセッションへ着地させるか」です。3パターンあります。

1. **既存セッションへの自己バインド**: 発火するたびに"同じ会話"が再開される。文脈を引き継いだ継続タスク(例: リマインダー、進行中プロジェクトの定期チェック)に向く
2. **指定した別セッションへバインド**: 自分が作った"兄弟セッション"を、別のセッションから定期的に起こす。監視役セッションと作業セッションを分けたい場合に使う
3. **毎回フレッシュなセッションを新規作成**: 発火のたびに文脈ゼロの新規セッションが立つ。前回の会話に依存しない独立タスク(例: 日次バッチ、定型レポート)に向く

ここで一番よくある事故は、**継続タスクのつもりで「毎回フレッシュ」を選んでしまう**ことです。フレッシュモードは会話の記憶を一切持たないため、プロンプト側に「何を前提に動くか」を毎回自己完結で書いておく必要があります。逆に自己バインド型は会話が積み重なる分、長期運用でコンテキストが肥大化しやすい点に注意が必要です。

## cron設定の落とし穴

Routine のスケジュールは cron 形式の5フィールド(分・時・日・月・曜日)で指定しますが、いくつか見落としやすい仕様があります。

- **すべて UTC で評価される**。日本時間の「毎朝8時」は `0 23 * * *`(前日23時UTC)のように変換してから設定する必要があります。日をまたぐ変換をするときは曜日・日付フィールドもズレることを忘れがちです
- **最小間隔は1時間**。分単位の細かい実行はできません
- **「毎時」「N時間おき」を分0で組むと、作成した瞬間の分を起点に均される**仕様があります。これは複数の Routine を一斉に0分へ集中させないための挙動なので、「なぜか指定通りの分ぴったりに動かない」と思っても壊れているわけではありません

一度作った Routine の cron やプロンプトを直したいときは、削除して作り直すのではなく **更新系のツールでその場を書き換える**のが無難です。実行履歴(run history)を保持したまま変更できるので、過去の実行ログを追いたいケースでは特に有効です。

## 通知設計: 「動いたこと」より「気づくべきこと」を届ける

フレッシュセッション型の Routine には、完了時に通知(プッシュ/メール)を出す設定があります。ここで大事なのは、**「実行が終わった」ことを毎回知らせるのではなく、「人間が今知るべきことがあるときだけ」知らせる**という設計方針です。

- 巡回して異常なし → 通知しない(サイレントに終える)
- 異常を検知した、判断が必要、実行自体ができなかった → 通知する

これを徹底しないと、「定期実行が動いている」という当たり前の事実の通知が積み重なって、本当に重要な通知が埋もれます。個人の通知許容量は有限なので、Routine 設計の初期段階で「毎回通知」をデフォルトにしないことをおすすめします。

## セッション回数そのものがコストになる場合の工夫

Claude Code の利用枠(メッセージ数・トークン数)が他の用途と共有になっている場合、Routine を思いつくままに増やすと枠を圧迫します。筆者が実際にやっている工夫は次の2つです。

1. **関連タスクは1つの Routine にまとめる**。「執筆」「レビュー」「公開」を別々の Routine に分けず、1回のセッションで一気通貫にやらせて、公開だけ日時指定で分散させる
2. **Routine の数を用途ごとに固定し、増やす前に既存の統合を検討する**。曜日ごとに役割を1つに絞ると、後から見たときにどの Routine が何をするものか把握しやすくなります

## まとめ

Routines を組むときに最初に決めるべきは「発火先セッションのモード」、次に注意すべきは「cronはUTC評価・最小間隔1時間」、そして運用が長くなるほど効いてくるのが「通知は本当に必要なときだけ」という設計です。定期実行タスクをこれから組む人の参考になれば幸いです。
