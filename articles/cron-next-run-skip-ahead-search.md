cron式から「次に実行される日時」を計算するロジックを自分で書くとき、最初に思いつくのは「1分ずつ時刻を進めながら、式にマッチするかを順番にチェックする」という素朴な全数探索です。実装はシンプルですが、「次回実行日時を10件先まで表示する」「何年も先まで一致しない不正な式を検出する」といった要件になると、この素朴な実装は簡単に遅くなります。cron式の次回実行日時計算ツールを作る過程でこの高速化を実装したので、考え方を整理します。

## 素朴な実装: 1分ずつ進めて判定する

```js
function findNextNaive(cron, from) {
  let candidate = new Date(from.getTime());
  candidate.setSeconds(0, 0);
  candidate.setMinutes(candidate.getMinutes() + 1);

  // 最大で8年分(うるう年を含めても足りる期間)を上限に探索
  const limit = new Date(from.getTime());
  limit.setFullYear(limit.getFullYear() + 8);

  while (candidate < limit) {
    if (matches(cron, candidate)) return candidate;
    candidate.setMinutes(candidate.getMinutes() + 1);
  }
  return null; // 一致しない(不正な組み合わせ)
}
```

これは「毎分実行」のような頻出パターンでは一瞬で終わりますが、「2月30日」のように**絶対に一致しない式**を渡すと、1分刻みで8年分(約420万分)を律儀に全部チェックしてから「一致しませんでした」と答えることになります。ブラウザのメインスレッドで動く静的ツールにとって、数秒単位のフリーズは致命的です。

## 気づき: 「どのフィールドが不一致か」が分かれば、次の候補まで直接ジャンプできる

全数探索が無駄なのは、「月が条件に合わない」と分かった瞬間に、その月のすべての分・時・日の組み合わせを1分ずつ律儀に試しているからです。月が不一致なら、その月の残りをどう探索しても一致するはずがありません。**不一致と分かった時点で、次に条件が変わり得るタイミングまで直接進めてしまえばよい**わけです。

具体的には、候補の日時を「分の不一致」「時の不一致」「日(または曜日)の不一致」「月の不一致」のどれに最初に引っかかったかで分類し、それぞれに応じたジャンプ先を決めます。

```js
function findNextFast(cron, from) {
  let candidate = roundUpToNextMinute(from);
  const limit = addYears(from, 8);

  while (candidate < limit) {
    if (!cron.month.includes(candidate.getMonth())) {
      candidate = startOfNextMonth(candidate); // 月が変わるまで丸ごとスキップ
      continue;
    }
    if (!matchesDate(cron, candidate)) {
      candidate = startOfNextDay(candidate); // 日付条件を満たさないので翌日0時へ
      continue;
    }
    if (!cron.hour.includes(candidate.getHours())) {
      candidate = startOfNextHour(candidate); // 時条件を満たさないので翌時0分へ
      continue;
    }
    if (!cron.minute.includes(candidate.getMinutes())) {
      candidate = addMinutes(candidate, 1); // 分だけの不一致はそのまま1分ずつ進める
      continue;
    }
    return candidate; // すべてのフィールドが一致
  }
  return null;
}
```

ポイントは、**粒度の粗いフィールド(月・日)の不一致は、粒度の粗い単位でジャンプする**ことです。月が合わなければ「来月1日0時0分」へ、日付条件(日・曜日のOR条件)が合わなければ「翌日0時0分」へと、一致条件を変える最小の単位まで一気に進めます。分フィールドだけは「この時間内の次の一致分」を探す必要があるので、最も細かい1分刻みのままにしています(多くの実装では、ここもビット演算で次の一致分を直接計算してさらに高速化できますが、分の範囲は0〜59しかないため1分刻みでも実用上のコストは小さく、今回は可読性を優先してシンプルな実装にとどめました)。

この方式だと、「2月30日」のような一致しない式は、月のチェック→日付のチェックで毎回即座に弾かれ、該当月を素通りし続けて最終的に探索上限(8年)に到達するまでに必要な反復回数は「年×12か月」程度まで減ります。1分刻みの全数探索(最大420万回)と比べて、桁違いに少ない反復で済みます。

## 注意点: ジャンプ先を戻すタイミングで下位フィールドをリセットし忘れる

このパターンを実装するときに最もハマりやすいのが、上位フィールド(日や月)をジャンプで進めたのに、下位フィールド(時・分)の値をリセットし忘れるバグです。

```js
// バグがある例: 日付を進めても時刻が元のままになっている
function startOfNextDayBuggy(date) {
  const d = new Date(date.getTime());
  d.setDate(d.getDate() + 1);
  return d; // 時・分・秒が元の値のまま残ってしまう
}
```

たとえば候補が「10月5日14時30分」で日付条件が不一致だった場合、単純に日だけ+1すると「10月6日14時30分」になります。本来探索したいのは「10月6日0時0分」から先のすべての時刻なのに、14時30分より前の時刻帯(0時〜14時29分)を見落としたまま次の判定に進んでしまいます。日・時・月をジャンプさせるときは、**それより下位のフィールドをすべて0にリセットする**ことを徹底する必要があります。

```js
function startOfNextDay(date) {
  const d = new Date(date.getTime());
  d.setDate(d.getDate() + 1);
  d.setHours(0, 0, 0, 0); // 下位フィールドを明示的にリセット
  return d;
}
```

## 検証: 「ジャンプしても結果が全数探索と一致するか」を突き合わせる

高速化のロジックはバグを仕込みやすいため、次の方法で検証しました。

- 頻出パターン(毎日・毎時・曜日指定など)で、素朴な全数探索版と高速化版の出力が完全に一致するか突き合わせる(高速化のためにロジックを変えても、結果は変わってはいけない)
- 「2月30日」のような一致しない式を渡し、8年分の探索上限まで短時間(体感で遅延なし)で打ち切られるか
- 日付条件の不一致から日単位でジャンプしたあと、その日の0時より前の時刻帯を見落としていないか(上記のリセット漏れバグの再発防止)
- 月をまたぐ・年をまたぐジャンプで、年月日のフィールドが正しく繰り上がるか

特に1つ目の「全数探索版との突き合わせ」は、高速化ロジックの正しさを担保する最も確実な方法です。素朴な実装は遅いだけで仕様としては正しいので、それ自体を「正解」として扱い、高速化版の出力と機械的に比較できます。

## まとめ

- cronの次回実行日時を1分刻みで全数探索すると、一致しない式を渡されたときに数百万回規模の無駄な反復が発生する
- 不一致になったフィールドの粒度(月・日・時・分)に応じて、次に条件が変わり得るタイミングまで直接ジャンプすることで反復回数を大幅に減らせる
- 上位フィールドをジャンプさせるときは、下位フィールドを明示的に0へリセットしないと時刻帯を見落とすバグになる
- 高速化ロジックの正しさは、遅いが仕様通りの全数探索版と出力を突き合わせることで検証できる

「遅いが確実に正しい実装」を先に用意し、それを基準に高速化版の正しさを検証する、というこの進め方自体も、計算ロジックを安全に最適化するときに汎用的に使えるパターンです。
