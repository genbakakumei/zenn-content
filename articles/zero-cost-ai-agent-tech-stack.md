## この記事について

AIエージェントに定期実行で何かを任せ続けようとすると、すぐに「どこにホスティングするか」「状態をどこに保存するか」「トリガーはどう組むか」という技術選定の問題にぶつかります。ここで安易にサーバーレス関数やマネージドDBを選ぶと、思わぬ従量課金や、エージェントが無自覚に使用量を伸ばしてしまうリスクを抱え込みます。

筆者は現在、AIエージェント(Claude)に「初期費用・固定費ゼロ」という制約のもとで個人開発の運用を任せる実験を進めています。この記事では、その中で実際に使ってきた技術選定の基準を、一般化できる形で整理します。有料サービスを使うなというより、**「無料枠の性質」を見極めて選ぶための判断軸**の話です。

## 基準1: 新規契約ではなく、既に持っているものを使い倒す

一番シンプルで見落としがちな基準です。GitHubアカウントを持っているなら、静的サイトホスティングはGitHub Pagesで足ります。GitHubと連携できる技術系ブログサービス(Zennなど)を使っているなら、pushするだけで公開できるパイプラインが既に手元にあります。チャット通知が必要なら、既存のSlackワークスペースへのDM送信で十分なことが多く、わざわざ通知専用のSaaSを新規契約する必要はありません。

新しいサービスを1つ増やすたびに、アカウント管理・認証情報・規約確認・そして「無料枠の崖」を再評価するコストが発生します。**既存の契約の組み合わせで達成できないかを先に検討する**のが、費用だけでなく運用の複雑さを抑える意味でも効きます。

## 基準2: 「無料枠→従量課金」の崖があるサービスは原則除外する

無料サービスには大きく2種類あります。

- **恒久的に無料**なもの(例: GitHub Pagesの静的ホスティング、パブリックリポジトリのGit LFS以外の容量など)
- **無料枠を超えると自動的に課金が発生する**もの(例: 多くのサーバーレス関数・マネージドDB・外部APIの従量課金プラン)

後者は、人間が使う分には「気づいたら止める」ができますが、**自律的に動くエージェントが使う場合は話が別**です。エージェントが想定より多くリクエストを発行したり、公開したツールに想定外のアクセスが集中したりすると、無自覚に無料枠を超えて課金が発生します。「費用ゼロ」を制約として掲げているなら、この種のサービスは次のどちらかでない限り採用しないのが安全です。

- **請求上限(ハードキャップ)を$0または任意の低い金額に設定できる**こと(超過時は停止であって課金ではない)
- そもそも**無料枠を使い切っても機能が停止するだけで課金されない**設計になっていること

ハードキャップの設定機能がないサービスは、たとえ無料枠が魅力的でも自律運用の技術選定からは外す、という運用にしています。

## 基準3: サーバー処理より、ブラウザ内(クライアントサイド)処理に倒す

以前、日本語LLMのトークン数を数えるWebツールを作った際、外部APIにテキストを送って数えさせる方式ではなく、トークナイザのライブラリをブラウザにバンドルしてクライアントサイドで完結させる方式を選びました(詳細は「[サーバーに送らずに正確なLLMトークン数を数える](https://zenn.dev/ykwlab/articles/bundle-tiktoken-for-browser-token-counter)」)。

この設計のポイントは、**アクセス数がいくら増えてもホスティング側のコストが増えない**ことです。静的ファイルを配信するだけなので、GitHub Pagesの無料枠の範囲で成立します。サーバー側で処理する設計だと、アクセスが増えるほど計算リソースやAPI呼び出しのコストが線形に増えていき、「無料で公開したはずが人気が出た途端に費用が発生する」という皮肉な事態になりかねません。**「バズっても費用が増えない」構成になっているか**は、費用ゼロ制約下では重要なチェックポイントです。

## 基準4: マネージドDBではなく、Gitをステートストアにする

エージェントが継続的に状態(進捗・アカウント状況・作業ログなど)を持つ必要がある場合、マネージドDBを使いたくなりますが、小規模な個人運用であれば**Gitリポジトリ内のMarkdown/YAMLファイルで十分**なことが多いです(この設計については「[記憶が消えるAIエージェントを『自律継続稼働』させる3つのファイルパターン](https://zenn.dev/ykwlab/articles/agent-continuity-file-patterns)」で詳しく扱いました)。

Gitをステートストアにすると、費用が発生しないだけでなく、**変更履歴がそのまま監査ログになる**という副次的なメリットもあります。「いつ、何が、どう変わったか」を人間が後から追いやすく、エージェントの判断を振り返る際にも役立ちます。

## 基準5: スケジュール実行は、既存の実行基盤に乗せる

定期実行の仕組みを自作しようとすると、サーバーを立てっぱなしにするかクラウドのcronサービスを使うことになり、どちらも費用や管理コストが発生します。すでにAIエージェントの実行環境自体にスケジュール実行の機能(定期起動の仕組み)が備わっているなら、それに乗せるのが最も費用がかからず、かつ実行環境の権限スコープをそのまま引き継げるので安全です(この仕組み自体の設定方法は「[Claude CodeのRoutines(スケジュール実行)でAIエージェントを定期起動する設定ガイド](https://zenn.dev/ykwlab/articles/claude-code-routines-guide)」を参照してください)。

## 基準6: 収益化のための投資は「初収益後の再投資」に限定する

独自ドメインの取得、ネイティブアプリのストア登録費用、有料広告など、収益に直結しそうでも初期費用がかかるものは、**最初の売上が立つまでは着手しない**という一線を引いています。無料でできる代替手段(サブディレクトリでの公開、PWA化、SNSでの無償告知など)で立ち上げ、実際に収益が出てから再投資の判断をする方が、費用ゼロという制約と矛盾しません。

## 判断のフレームワーク

これまでの基準をまとめると、次のような判定表になります。

| サービス・手法の例 | 無料枠の性質 | 判定 |
|---|---|---|
| GitHub Pages(静的ホスティング) | 恒久的に無料 | 採用 |
| GitHub連携の技術ブログ(push=公開) | 恒久的に無料 | 採用 |
| クライアントサイド処理(ブラウザ内完結) | ホスティング費用が発生しない | 採用 |
| Gitリポジトリをステートストアに使う | 恒久的に無料 | 採用 |
| 既存の実行環境のスケジュール機能 | 追加費用なし | 採用 |
| サーバーレス関数・マネージドDBの無料枠 | 従量課金の崖あり | ハードキャップ($0)がなければ不採用 |
| 外部LLM APIの従量課金 | トークン従量課金 | 不採用(クライアントサイド処理に倒す) |
| 独自ドメイン・ネイティブアプリのストア登録 | 初期費用が発生 | 初収益後の再投資として保留 |

## まとめ

- 新しいサービスを増やす前に、既に持っている契約の組み合わせで達成できないか検討する
- 「無料枠→従量課金」の崖があるサービスは、ハードキャップを設定できない限り自律運用の選定から外す
- アクセスや利用が増えても費用が増えない構成(クライアントサイド処理・静的ホスティング)を優先する
- 状態管理はマネージドDBではなくGitで、スケジュール実行は既存の実行基盤で済ませる
- 収益化のための投資は、初収益が立ってからの再投資に限定する

費用ゼロという制約は不便なようで、実は「使い切っても壊れない構成」を強制してくれるので、個人開発の技術選定を単純化してくれる面もあると感じています。
