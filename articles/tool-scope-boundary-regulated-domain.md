工数計算やcron式のような「入力がそのまま数式に落ちる」ツールと違い、労務・法律・税務のように制度が絡む領域のツールは、同じ「計算する」でも一段扱いが難しくなります。制度上のルールは明確でも、ユーザーの個別事情まで含めて100%正しい結果を返せるとは限らないからです。有給休暇の付与日数を計算するツールを作った際に、この「どこまで計算していいか」の線引きで迷った部分を、判断基準として整理します。

## 制度のルールと、個別事情への依存は別物

有給休暇の付与ルールは労働基準法39条に条文があり、次の2つは条文から機械的に計算できます。

- 入社日から6か月後、以降12か月ごとの「基準日」(月末入社時のうるう年ケースを含む日付計算は[前回の記事](https://zenn.dev/ykwlab/articles/js-safe-add-months-date-calculation)で扱いました)
- 週所定労働日数に応じた付与日数(通常勤務は10〜20日、比例付与対象は労基法別表の日数)

一方、この付与ルールには「全労働日の8割以上出勤していること」という適用条件が付いています。この出勤率は、育休・産休・休職・私傷病といった個別の休業事情によって計算方法が変わり、**入社日と雇用形態だけからは判定できません**。つまり同じ「有給休暇の計算」という機能の中に、条文から機械的に確定できる部分と、ユーザー個人の事情がないと確定できない部分が混在しています。

この区別を曖昧にしたまま両方を同じ確信度で表示すると、後者(出勤率が絡むケース)まで「計算済みの正しい答え」に見えてしまい、実態と違う数字をユーザーが信じてしまうリスクがあります。

## 判断基準: 3つに仕分ける

個人開発でこの手の領域のツールを作るとき、機能を作り込む前に、盛り込みたい計算を次の3種類に仕分けています。

1. **入力から一意に決まり、検証可能な計算** → そのまま実装する(基準日・付与日数・時効消滅日など)
2. **入力だけでは決まらないが、条件を明示すれば計算範囲を限定できるもの** → 前提条件をチェックボックス等で明示し、外れたら警告表示に切り替える(出勤率8割要件がこれに当たる)
3. **個別の専門判断が必要で、ツールの入力粒度では原理的に確定できないもの** → 計算せず、「専門家に確認を」という注記に留める(休職期間の出勤率個別計算、解雇予告手当の個別事情など)

これは「機能を削る」判断ではなく、「確信度が違う情報を同じ見た目で出さない」判断です。3の領域まで無理に数値化すると、一見親切な機能に見えても、外れたときの実害(誤った数字を信じて労務対応を誤る)の方が大きくなります。

## 実装への落とし方

3種類の仕分けは、UIの状態遷移としてそのまま実装に落とせます。

```js
// 「出勤率8割以上」の前提が外れたら、確信度の高い表示から警告表示へ切り替える
if (!attendanceOkEl.checked) {
  resultBoxEl.classList.add('is-warning');
  resultBoxEl.textContent =
    '出勤率の条件を満たさない可能性があるため、この表の日数は参考値です。個別の出勤率計算は専門家に確認してください。';
} else {
  resultBoxEl.classList.remove('is-warning');
  renderScheduleTable(); // 条文から機械的に確定できる計算のみを表示
}
```

ポイントは、警告状態でも数値を消してしまわないことです。数値そのものは条文ルール通りに計算されているので、「前提条件付きの参考値である」ことを明示した上でそのまま見せた方が、ユーザーが自分の状況と照らし合わせて判断しやすくなります。消してしまうと、なぜ消えたのかが伝わらず、かえって不親切になります。

## まとめ

- 制度が絡む領域のツールでは、「条文から機械的に決まる部分」と「個別事情がないと決まらない部分」が同じ機能の中に混在しやすい
- 作り込む前に、計算を「そのまま実装」「条件明示+警告切り替え」「専門家への注記に留める」の3段階に仕分けると、確信度の異なる情報を同じ確信度で見せてしまう事故を防げる
- 前提条件が外れたときは数値を隠すのではなく、警告表示に切り替えて「参考値であること」を明示する方が、機能としても誠実さとしても筋が良い
