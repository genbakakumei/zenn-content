静的な計算ツールにユニットテストを書くとき、「期待値」をどこから持ってくるかで、そのテストの意味がまったく変わります。実装者の頭の中にある期待値を期待値としてそのままテストに書き写すと、実装のミスとテストのミスが一致していた場合に検出できません。有給休暇・工数計算など、法律や公開された計算根拠がある領域のツールを作る中で固めた、「何を基準値(テストオラクル)にするか」の考え方を整理します。

## 自分の期待値を自分でテストする、という循環

次のようなテストは、一見ちゃんと検証しているように見えます。

```js
test('6ヶ月勤続で10日付与される', () => {
  expect(grantDays(0.5)).toBe(10);
});
```

しかし `10` という期待値が「実装者が labor law を思い出しながら書いた数字」である場合、実装側の計算ロジックに勘違いがあれば、同じ勘違いのままテストの期待値も書いてしまう可能性が残ります。ユニットテスト自体は「実装とテストの期待値が一致している」ことしか保証しておらず、「その値が実際に正しい」ことまでは保証しません。これは個人開発の計算ツールに限らず、テスト全般に言える制約ですが、法律・制度のように**外部に唯一の正解が存在する**領域では、この制約を埋める具体的な手段があります。

## 3種類の基準値を使い分ける

実際にWebツール群(有給休暇計算・工数計算)を検証する際に使っている、期待値の出どころは大きく3種類です。

| 基準値の種類 | 具体例 | 検出できるバグ |
|---|---|---|
| 1. 法令・公開された数表そのもの | 労働基準法の比例付与日数表、各値をそのまま転記 | 実装者の思い込みによる数表の誤転記・誤実装 |
| 2. 手計算(電卓・紙) | 入社日から8回分の基準日・付与日数を自分で計算し直す | ロジックの実装ミス(日付計算・分岐の誤り) |
| 3. 既知の境界値(うるう年・月末日) | 2023-08-31入社+6ヶ月が2024-02-29になるか | 日付計算ライブラリ・自作ロジックの境界バグ |

重要なのは、どの基準値も**実装コードを一切経由せずに得られる**という点です。法令の数表はそのまま転記するだけで計算不要、手計算は実装と独立した経路で同じ答えにたどり着く確認、境界値は「2024年がうるう年である」という外部事実から逆算した期待値です。実装のコピーになっていない期待値だけが、実装のバグを検出できます。

## 実例: 有給休暇計算ツールでの基準値の当て方

有給休暇計算ツールの検証では、2020-04-01入社・通常の労働者という設定で、8回分の基準日・付与日数(10→11→12→14→16→18→20→20日)を手計算し、実装の出力と突き合わせました。比例付与(週2日・週3日勤務)の日数表は、労働基準法の別表の数値をそのまま転記して突き合わせています。さらに、月末入社(2023-08-31)から6ヶ月後がうるう年の2月末(2024-02-29)に正しく丸まるかという、カレンダーの境界だけを狙った確認も別途行っています。

この3つはそれぞれ別のバグを検出する設計になっています。手計算との突き合わせだけでは比例付与表の転記ミスは見つかりませんし、数表の転記確認だけでは日付計算のロジックバグは見つかりません。どれか1つだけでは「テストが通っている」という安心感だけが残り、カバーできていない種類のバグが未検出のまま残ります。

## ユニットテストが書きにくい静的ツールでの代替

これらのWebツールは1ファイル完結のテスト基盤を持たないため、Playwrightで実際にブラウザを操作し、画面に表示された値を上記の基準値と目視・スクリプトで突き合わせる形で検証しています。テストフレームワークの有無にかかわらず、「どの基準値と突き合わせているか」さえ明確なら、簡易な確認でも検出力は確保できます。逆にテストコードとして整備されていても、期待値の出どころが実装者の記憶だけなら、前述の循環から逃れられません。

## まとめ

- 計算ツールのテストは、期待値の出どころが実装コードと独立していなければ、実装のバグを検出できない
- 法令・公開された数表、手計算、既知の境界値(うるう年等)という3種類の基準値は、それぞれ別の種類のバグを検出する
- テストフレームワークの有無よりも、「何と突き合わせているか」が検証の信頼性を決める

静的な計算ツールの「正しさ」をどう担保するかという話は、有料本「個人開発Webツールの『誠実な設計』実践ガイド」でも扱っている予定です。
