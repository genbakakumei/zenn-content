GitHub Pagesで静的ツールを公開する、という戦略自体は「ホスティング費用がゼロ」というだけの話でよく語られます。しかし、ツールを1本ではなく5本、10本と増やしていくと、ホスティング費用以外のところで「費用ゼロ」を維持するのが徐々に難しくなる場面が出てきます。複数の静的ツールを運用してきて実際に効いた、実装段階での制約をまとめます。

## 「1本なら問題ない」が積み重なると効いてくること

- **外部CDNへの依存**: 1本だけならCDNの可用性・レート制限を気にしなくても動きますが、本数が増えるほど「そのCDNが落ちた/変更された」ときの影響範囲が広がります。ライブラリは `vendor/` にバンドルして同梱し、実行時に外部を一切参照しない構成にしています
- **外部APIの呼び出し**: 無料枠のAPIは便利ですが、複数ツールで共有すると1本のアクセス増加が他のツールの無料枠を消費します。計算がブラウザ内で完結する設計にしておけば、この結合自体が発生しません
- **デザインシステムの重複**: ツールごとにCSSを書き直すと、ダークモード対応やレスポンシブ対応の考慮漏れがツールの数だけ発生します。共通のCSS変数(配色・余白・フォントサイズ)を1セット用意し、全ツールで使い回しています

## 実装レベルでの3つの制約

複数の静的ツールを気持ちよく増やしていくために、新しいツールを作るときに次の3つを固定ルールにしています。

### 1. 外部依存はビルド時に閉じ込める、実行時には残さない

npmパッケージを使う場合でも、esbuild等でバンドルしてリポジトリに同梱し、ブラウザが実行時にfetchするのは自分のドメイン(GitHub Pages)のファイルだけにします。トークンカウンターのtiktokenバンドル(4.4KB)がこの例です。「ビルド時に外部の力を借りるが、実行時は自己完結する」という線引きです。

```
products/web-tools/token-counter/
  vendor/
    tiktoken.bundle.js   # ビルド済み、実行時はここだけ参照
    ranks/
      o200k_base.tiktoken
```

### 2. サーバーを持たない設計を、機能追加のたびに再確認する

「ちょっとした集計くらいならサーバーに送った方が楽」という誘惑は、機能を追加するたびに出てきます。しかしサーバーを1つ持つと、その瞬間から可用性・スケール・セキュリティという費用ゼロでは済まない責務が発生します。既存ツールは全て入力データを外部に送信しない設計にしており、新機能を足すときも「ブラウザ内の計算で実現できないか」を先に検討してから着手しています。

### 3. 共通コンポーネントは「後で共通化」ではなく最初から共有ディレクトリに置く

5本のツールはそれぞれ別ディレクトリで開発していますが、配色・カード・警告バッジといった見た目のコンポーネント(前回の記事で書いた確信度の3状態表示など)は、コピペで増やすと直す時に5箇所を直す羽目になります。共通CSSとして1箇所にまとめ、各ツールから参照する構成にしておくと、デザインの一貫性を保つコストがツールの本数に比例して増えずに済みます。

## まとめ

- 「費用ゼロ」はホスティング代だけの話ではなく、外部CDN・外部API・重複実装のような、本数が増えるほど効いてくる間接コストも含めて維持する必要がある
- 外部依存はビルド時に閉じ込めて実行時には残さない、サーバーを持たない設計を機能追加のたびに再確認する、共通コンポーネントは最初から共有する、の3つを固定ルールにすると、ツールの本数を増やしても運用コストが線形以上には増えない

こうした技術選定の考え方は、有料本「[AIエージェント自律運用実践ガイド](https://zenn.dev/ykwlab/books/ai-agent-autonomous-ops-guide)」の7章「費用ゼロで組む技術選定」でも扱っています。今回の話はその実装版として、静的Webツールを複数本運用する場面に絞って掘り下げたものです。
