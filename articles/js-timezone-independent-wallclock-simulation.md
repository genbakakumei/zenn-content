「このcron式はUTCで評価されるが、日本時間だと何時に動くのか」「サーバーのタイムゾーン設定に関わらず、常に東京時間での結果を出したい」。日時を扱うツールを作っていると、こういう要件に必ず当たります。

厄介なのは、**この計算をブラウザやNode.jsの実行環境のタイムゾーン設定に依存させてはいけない**ことです。閲覧者のPCが日本時間でも、アメリカ西海岸時間でも、同じ入力に対して同じ結果を返さなければ、ツールとして成立しません。「cron式の次回実行日時計算ツール」をUTC/JST両対応で実装する際にこの問題を詰めたので、使った実装パターンを整理します。

## 何がダメなのか: `Date`はいつも「実行環境のローカル時刻」を返す

JavaScriptの`Date`オブジェクトは、生成した瞬間の時刻を内部的にはUTCのタイムスタンプ(エポック秒)として保持していますが、`getHours()`や`getDate()`のような「タイムゾーンなし」のゲッターは、**実行環境(ブラウザ・OS)に設定されたローカルタイムゾーン**を使って値を返します。

```js
const d = new Date("2026-10-15T00:00:00Z"); // UTC深夜0時
console.log(d.getHours()); // 実行環境がJSTなら9、PSTなら16や17…結果が環境依存
```

サーバーサイドのNode.jsならタイムゾーンを固定できますが、ブラウザで動く静的ツールは閲覧者のOS設定を変えられません。「JSTでの計算結果を見せたい」のに、閲覧者の設定次第で違う答えが返ってくるようでは、計算ツールとして信頼できません。

`Intl.DateTimeFormat`に`timeZone`オプションを渡す方法もありますが、文字列のフォーマットと再パースを挟むため、分単位の繰り返し計算(次回実行日時を10件求めるなど)には不向きです。もっと直接的に、数値としての日時を任意タイムゾーンで扱いたいケースに向くパターンを紹介します。

## パターン: `getUTC*`/`setUTC*`で「決め打ちタイムゾーンの壁時計」をシミュレートする

鍵になるのは、`Date`には実行環境に依存しない`getUTC*`/`setUTC*`系メソッドが用意されている、という点です。これを使えば「本当のUTC」ではなく「**任意の固定タイムゾーンでの壁時計**」を、実行環境の設定を一切参照せずに扱えます。

考え方はこうです。

1. 本当のUTC時刻に、評価したいタイムゾーンのオフセット(分)を加算した「ずれた時刻」を作る
2. この「ずれた時刻」に対して`getUTC*`系のゲッターを使うと、**UTCメソッドなのに実質そのタイムゾーンでの壁時計の値が読める**
3. 値を書き換えたいときも同様に、`setUTC*`系で「ずれた時刻」側を操作してから、最後にオフセットを引き戻して本当のUTCに戻す

```js
const OFFSETS_MIN = { UTC: 0, JST: 540 }; // JSTはUTC+9時間 = 540分

// 本当のUTC時刻 → 指定タイムゾーンの「壁時計」を表すDateへ変換
function toWallClock(utcDate, tz) {
  return new Date(utcDate.getTime() + OFFSETS_MIN[tz] * 60_000);
}

// 壁時計を表すDateから、UTCの各フィールドを読めば
// そのままそのタイムゾーンでの時刻フィールドになる
function wallClockHour(utcDate, tz) {
  return toWallClock(utcDate, tz).getUTCHours();
}

// 壁時計側で値をセットしたら、オフセットを引いて本当のUTCに戻す
function setWallClockField(utcDate, tz, setter) {
  const wall = toWallClock(utcDate, tz);
  setter(wall); // wall.setUTCHours(0) などを呼ぶ
  return new Date(wall.getTime() - OFFSETS_MIN[tz] * 60_000);
}
```

これで、実行環境のタイムゾーン設定を一度も参照せずに、「JSTでの0時」「UTCでの9時」といった値を数値計算だけで扱えます。閲覧者がどこの国からアクセスしていても、同じ入力に対して完全に同じ結果を返せるようになりました。

## なぜこれで正しく動くのか

`getUTC*`/`setUTC*`は「このDateオブジェクトが指すエポック時刻を、UTCという基準で見た場合の年月日時分秒」を返すだけの、タイムゾーン変換を一切行わない生のアクセサです。つまり`Date`オブジェクト自体には「ずらした時刻」も「本当のUTC時刻」も区別がなく、**どちらの意味で使うかはこちらが決めてよい**という性質を利用しています。

「UTC+9時間ずらした時刻」に対して`getUTCHours()`を呼べば、返ってくる数値は「本来のJST時刻の時」と一致します。オフセットの加算・減算というシンプルな数値演算だけで、タイムゾーン変換のロジックをすべて完結させられるのがこのパターンの利点です。ライブラリに依存せず、`Date`の組み込みメソッドだけで実装できます。

## 固定オフセットで扱える範囲と、扱えない範囲

このパターンが成立するのは、**対象のタイムゾーンが夏時間(DST)を持たず、UTCからのオフセットが常に一定**である場合です。日本時間(JST、UTC+9固定)はこの条件に当てはまるため、今回のツールのようにUTC/JSTの2択で十分な用途にはシンプルにフィットします。

逆に、アメリカやヨーロッパの大半のタイムゾーンのように夏時間で年2回オフセットが変わる地域を扱う場合、固定オフセットのこの実装では日付によって答えがずれてしまいます。その場合は素直に`Intl.DateTimeFormat`のタイムゾーン変換機能(IANAタイムゾーンデータベースを内蔵している)を使うべきで、自前でDSTの切り替え日を計算するのは車輪の再発明になります。「固定オフセットで足りる用途かどうか」を実装前に見極めることが、このパターンを選ぶかどうかの分岐点です。

## 検証: オフセットの往復を手計算値と突き合わせる

このパターンはオフセットの加算・減算が逆向きになっている箇所で間違えやすいため、次のケースを手計算値と突き合わせて確認しました。

- UTC 0:00 → JST表示で9:00になるか(UTC→壁時計方向)
- JST 0:00を指定して検索した結果が、UTCに戻すと前日15:00になるか(壁時計→UTC方向)
- 日付をまたぐケース(UTC 20:00 = JST翌日5:00)で、年月日のフィールドも正しく繰り上がるか
- UTC/JSTそれぞれを基準タイムゾーンとして選択したとき、同じ入力に対して一貫した結果が返るか(評価タイムゾーンの切り替えで実装が片方にしか対応していない、という事故を防ぐ)

特に3つ目の「日付をまたぐケース」は、時刻だけ合っていて日付のずれを見落としたまま通ってしまうテストになりがちなので、意識的にテストケースへ含める必要があります。

## まとめ

- `Date`の`getHours()`のような非UTC系メソッドは実行環境のローカルタイムゾーンに依存するため、静的な計算ツールでは使うべきではない
- `getUTC*`/`setUTC*`に固定オフセットを加減算することで、実行環境の設定を一切参照しない「任意タイムゾーンでの壁時計シミュレーション」が実装できる
- このパターンが成立するのは対象タイムゾーンのオフセットが一定(DSTなし)の場合に限られ、夏時間を持つタイムゾーンでは`Intl.DateTimeFormat`に任せるべき
- 日付をまたぐケースを含めて、オフセットの往復を手計算値と突き合わせて検証する

ブラウザで完結する日時計算ツールは、閲覧者の環境に関わらず同じ答えを返せて初めて信頼されます。実行環境のタイムゾーンに依存しない実装は、地味ですが外せない設計判断です。
