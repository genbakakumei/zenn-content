## この記事について

「AとBのどちらを入力してもいい。片方を入れたらもう片方を自動計算してほしい」というフォームは実務でよく出てきます。摂氏⇔華氏、税抜⇔税込、数量⇔単価、人数⇔作業日数など、2つの値が数式で結びついていて、どちらを「入力」として扱うかがユーザー次第になるケースです。

筆者は個人開発で工事現場向けの人工数計算ツールを作った際、「現場の人数」と「目標工期」のどちらを入力しても、もう一方を実稼働率込みで逆算する機能を実装しました。この記事では、そこで使った実装パターンと、素直に書くとハマる落とし穴についてまとめます。

## 素直に書くと壊れる: 相互監視の無限ループ

最初に思いつくのは、両方の入力欄に `input` イベントを張り、片方が変わったらもう片方の値を計算してセットする方法です。

```js
fieldA.addEventListener("input", () => {
  fieldB.value = calcBFromA(fieldA.value);
});
fieldB.addEventListener("input", () => {
  fieldA.value = calcAFromB(fieldB.value);
});
```

これは一見動きますが、`fieldB.value = ...` によるプログラムからの値設定でも `input` イベントが発火する実装(フレームワークによっては発火する)だと、A→B→A→B…と無限ループに陥ります。素のDOMの `.value` 代入では `input` イベントは発火しませんが、Reactの制御コンポーネントのように「値の変更を state 経由で反映する」実装だと容易にループします。

## パターン: 「今どちらが入力元か」を明示的に持つ

対策は、**「今この瞬間、どちらのフィールドがユーザー入力の起点か」を状態として持つ**ことです。片方の入力ハンドラの中で、もう片方への書き込み中だけガードフラグを立てておきます。

```js
let isSyncing = false;

function syncFrom(sourceField, targetField, calc) {
  sourceField.addEventListener("input", () => {
    if (isSyncing) return;
    isSyncing = true;
    targetField.value = calc(sourceField.value);
    isSyncing = false;
  });
}

syncFrom(fieldA, fieldB, calcBFromA);
syncFrom(fieldB, fieldA, calcAFromB);
```

これで「Aを編集 → Bを再計算」と「Bを編集 → Aを再計算」が独立して動き、互いの書き込みが相手のハンドラを再度起動しません。3つ以上のフィールドが絡む場合も同じ発想で、**「今どのフィールドが編集中か」を1つの変数(または状態)にまとめて、それ以外は常に導出値として再計算する**設計にすると破綻しにくくなります。

## 実稼働率のような「補正係数」を挟む場合

今回のツールでは、単純な四則演算の逆算だけでなく、「実稼働率(雨天・休工を考慮した稼働日の割合)」という補正係数を挟んで、人数⇔工期を相互に逆算する必要がありました。

```js
// 総人工数(人日)が決まっている前提で、人数⇔工期を逆算
function daysFromWorkers(totalManDays, workers, operationRate) {
  if (workers <= 0 || operationRate <= 0) return null;
  return Math.ceil(totalManDays / (workers * operationRate));
}

function workersFromDays(totalManDays, days, operationRate) {
  if (days <= 0 || operationRate <= 0) return null;
  return Math.ceil(totalManDays / (days * operationRate));
}
```

補正係数(ここでは実稼働率)が変わったときも、**「最後に編集されたフィールドを基準に、もう一方を再計算する」**というルールを一貫させることが重要です。両方を同時に再計算しようとすると、丸め誤差の蓄積でどちらが正なのか分からなくなります。今回は「最後にユーザーが直接編集した値を常に正とし、もう一方だけを導出値として書き換える」という一方向のルールに固定しました。

## 不正値のガード

逆算系のフォームでは、ゼロ除算や負の値の扱いを早めに決めておく必要があります。今回は次のルールにしました。

- 分母になり得る値(人数・工期・実稼働率)が0以下の場合は計算をスキップし、結果欄を空表示にする(`NaN` や `Infinity` を画面に出さない)
- 数量などの入力値が負の場合は、その行を合計計算から除外する(誤った過小評価より、明示的に「この行は無視されている」と分かる方が安全)

「入力が不正な場合に何を表示するか」は地味ですが、見積もり系のツールでは誤った数値を出すことが一番のリスクなので、実装の早い段階でルールを決めておくと後から迷いません。

## 検証: 両方向でテストする

このパターンはロジック上「A→B」と「B→A」の2方向があるため、片方向だけテストして満足しがちです。実際にはPlaywrightなどでブラウザを操作し、次の組み合わせを確認するのがおすすめです。

- Aを入力してBが正しく計算されるか
- Bを入力してAが正しく計算されるか
- 補正係数(実稼働率など)を変更したときに、直前に編集した方の値が保持されたまま、もう一方だけが再計算されるか
- 不正値を入力したときに無限ループやNaN表示が起きないか

## まとめ

- 双方向入力フォームを素直に相互監視で書くと、フレームワークによっては無限ループに陥る
- 「今どちらが入力元か」をガードフラグや状態として明示的に持つと安全に実装できる
- 補正係数を挟む場合も「最後に編集した方を正として、もう一方だけを導出する」ルールを一貫させる
- 分母がゼロになるケースと不正値の扱いは、実装の早い段階でルールを決めておく

摂氏⇔華氏のような単純な変換から、複数の補正係数が絡む逆算計算まで、同じ考え方で実装できるパターンです。
